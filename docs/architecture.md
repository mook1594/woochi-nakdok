# Architecture: nakdok

## 파이프라인

```
book.txt
  │
  ├─ [analyze] ─────────────────────────────────────────
  │    인코딩 감지 → 챕터 분할 → 문장 분할 → 청크 묶기
  │    (Phase 3) 세그먼트 분류 → 화자 판별 → 보이스 배정
  │    ↓
  │  .nakdok/manifest.json   ← SSOT
  │
  ├─ [synth] ───────────────────────────────────────────
  │    치환 사전 적용 → text_hash 계산 → 캐시 확인
  │    → 미스만 supertonic 합성 → wav 저장
  │    ↓
  │  .nakdok/audio/<hash>.wav
  │
  └─ [build] ───────────────────────────────────────────
       무음 삽입 → ffmpeg concat → AAC 인코딩 → 챕터 메타
       ↓
     book.m4b
```

세 단계가 각각 독립 실행 가능하고, 각 단계의 출력이 파일로 남는다. 문제가 생기면
어느 단계의 산출물이 잘못됐는지 파일을 열어 확인할 수 있다.

## 핵심 결정과 근거

### D1. 배치 생성, 실시간 스트리밍 아님

텍스트가 불변이므로 같은 문장을 두 번 합성할 이유가 없다. 오프라인 재생이
오디오북 사용 패턴의 대부분(이동 중 청취)을 차지하고, 실시간 생성은 서버 연결에
의존한다. 홈서버에서 llama-server와 CPU를 경쟁하는 문제도 배치가 유리하다.

속도는 병목이 아니다. Supertonic 3은 M4 Pro CPU 기준 RTF 0.012~0.015로 측정됐고,
i7-13700H에서 RTF 0.03을 가정해도 10시간 분량이 20~30분에 나온다.

### D2. 자체 플레이어를 만들지 않는다

m4b는 챕터 메타데이터를 담는 컨테이너이고, 기존 오디오북 앱(Smart AudioBook
Player, Voice, Apple Books 등)이 재생위치 기억·배속·슬립타이머를 이미 제공한다.
이 프로젝트는 웹앱이 아니라 변환기다. 라이브러리 UI가 필요해지면 Phase 4에서
얹는다.

### D3. TTS는 Supertonic 3

| 후보 | 판단 |
|---|---|
| **Supertonic 3** | 채택. 99M 파라미터, ONNX Runtime, 31개 언어(한국어 포함), 텍스트 정규화 내장, v2 대비 반복·누락 실패 감소 |
| Kokoro-82M | 폴백 후보. Apache 2.0로 라이선스는 더 자유롭지만 다국어 음성이 장문 합성에서 불안정하다는 보고가 있다 |
| XTTS v2 | 제외. 클로닝 품질은 좋으나 라이선스(CPML) 제약 |
| Chatterbox | 제외. 영어 중심 |

라이선스: 샘플 코드 MIT, 모델 가중치 OpenRAIL-M(사용 제한과 저작자 표시 요건
포함). 개인 사용에는 문제없으나 배포 시 확인 필요.

**실측 (supertonic 1.3.1 휠 직접 확인, 2026-08-28)**

| 항목 | 값 |
|---|---|
| 라이브러리 API | `TTS().synthesize(text, voice_style, speed, lang, total_steps, max_chunk_length)` |
| 보이스 | `get_voice_style("M1")` — M1–M5 / F1–F5 |
| duration | 반환된 wav 배열에서 `len(wav) / sample_rate`로 산출. ffprobe 불필요 |
| speed | 0.7 ~ 2.0, 기본 **1.05** |
| total_steps | 기본 8, 최대 100 — 품질/속도 노브. Phase 0 조정 대상 |
| 한국어 청크 | `DEFAULT_MAX_CHUNK_LENGTH_KO = 120` (D5의 근거) |
| 모델 가중치 | `auto_download=True`가 기본 — 별도 내려받기 절차가 필요 없다 |
| 스레드 제어 | `intra_op_num_threads` / `inter_op_num_threads`, 환경변수 `SUPERTONIC_INTRA_OP_THREADS` |
| wav 저장 | `save_audio()`는 `soundfile`을 요구한다 — 별도 설치 |

초안에는 채택 근거에 "C#/.NET SDK 공식 지원"이 있었다. 오케스트레이터를 Python으로
정하면서 불필요해졌고 검증되지도 않았으므로 삭제했다.

**리스크**: 한국어 낭독 톤이 장시간 청취에 견딜 수준인지가 이 프로젝트 전체의
단일 최대 리스크다. Phase 0에서 먼저 검증한다.

### D4. 오케스트레이터는 Python — TTS를 인프로세스로 부른다

supertonic이 Python 패키지이므로, 오케스트레이터를 Python으로 쓰면 사이드카가
통째로 사라진다. `supertonic serve`도 패키지에 들어 있지만 쓰지 않는다.

없어지는 것: 프로세스 기동·감시·재시작, 포트 점유 확인, 헬스체크, HTTP 타임아웃,
wav 바이트의 직렬화 왕복. 함수 호출에는 네트워크 실패가 없으므로 재시도 계층도
불필요하다 — R5의 지수 백오프 조항을 이 결정에 따라 삭제했다.

**후보 비교** (숙련도를 제외한 기술 기준)

| | Python | Rust | C# |
|---|---|---|---|
| supertonic 연동 | `import` — 사이드카 없음 | HTTP 사이드카 필수 | HTTP 사이드카 필수 |
| 한국어 문장 분할·형태소 | kss / kiwipiepy | 없음 | 없음 |
| "120자" 계산 (R3.4) | `len(s)` = 코드포인트 | 바이트 경계 주의 | UTF-16 단위 |
| 단일 바이너리 배포 | ✗ | ✓ 그러나 무의미 | ✓ 그러나 무의미 |
| 실행 속도 | 무관 | 무관 | 무관 |

성능은 판단 근거가 아니다. 실행 시간의 대부분을 ONNX 추론과 ffmpeg가 쓰고,
오케스트레이터가 하는 일은 파싱·해싱·JSON 쓰기·프로세스 호출이다.

Rust의 유일한 강점인 단일 정적 바이너리는 여기서 상쇄된다 — supertonic이 Python
패키지라 Rust로 짜도 Python 런타임이 배포 단위에 남는다. Rust가 이기려면 `ort`로
ONNX를 직접 돌려 Python을 제거해야 하는데, 그러려면 supertonic의 한국어 텍스트
정규화·G2P·토크나이저를 포팅해야 한다. 그건 D3이 채택 근거로 삼은 "텍스트 정규화
내장"을 스스로 버리는 것이고, 이 프로젝트의 최대 리스크를 정면으로 키운다.

초안에는 "Steno에서 whisper-server를 붙인 것과 동일한 패턴이라 운영 방식도
재사용된다"고 적혀 있었다. `mook-notes/own/now.md` 기준 woochi-steno는 설계만
확정되고 앱 코드가 0줄이므로 재사용할 대상이 없다. 근거를 삭제했다.

llama-server와 CPU를 나눠 쓸 때는 프로세스 affinity 대신 `intra_op_num_threads`를
쓴다 (D3 실측표).

### D5. 청크 = 문장이 아니라 문단 근처

문장마다 잘라 합성하면 문장 간 운율이 리셋되어 톤이 끊긴다. Supertonic은 한국어에서
`max_chunk_length`를 120자로 잡는다 (`DEFAULT_MAX_CHUNK_LENGTH_KO = 120`, 실측 확인).
그보다 크게 묶어도 내부에서 다시 잘린다. 따라서 **문장 경계에 맞춰 120자 근처까지
누적**하는 것이 최적이다.

120자를 넘기면 안 되는 이유가 하나 더 있다. `synthesize()`는 내부 재분할 지점마다
자체 `silence_duration`을 끼워 넣는데, 이 무음은 D6의 무음 정책 밖에 있어 우리가
제어하지 못한다. 청크를 120자 아래로 유지하면 재분할 자체가 일어나지 않아 무음이
전부 코드 관할로 들어온다.

문단 경계는 넘지 않는다. 문단이 바뀌면 청크도 끊는다 — 무음 정책을 적용할
지점이 필요하기 때문이다.

### D6. 무음은 코드가 넣는다

TTS는 문단이나 장면 전환의 쉼을 만들어주지 않는다. 자동 생성 오디오북이 듣기
힘든 가장 흔한 원인이 여기다.

| `boundary_after` | 기본값 | 판정 기준 |
|---|---|---|
| `sentence` | 400ms | 같은 문단 안에서 다음 청크로 이어짐. 청크 내부는 TTS가 처리 |
| `paragraph` | 800ms | 줄바꿈 1개 |
| `scene` | 1800ms | 빈 줄 2개 이상 연속 |
| `chapter` | 1000ms | 챕터가 바뀜 |

**판정은 `analyze`가 하고 `build`는 읽기만 한다.** 경계 종류는 원문의 줄바꿈
구조를 봐야 알 수 있는데 그 정보는 청크로 쪼개는 순간 사라진다. 그래서 청크마다
`boundary_after`를 매니페스트에 남긴다 (R3.7, R4.2). 이렇게 두면 `build`가 원문
txt를 다시 열 필요가 없고, 분할 로직이 파이프라인에 두 벌 생기지도 않는다.

우선순위는 `chapter` > `scene` > `paragraph` > `sentence`다. 마지막 청크는
`chapter`로 두되, 무음은 청크 **사이**에만 들어가므로 실제로는 쓰이지 않는다.

이 값은 취향이므로 설정으로 노출한다. Phase 1 완료 후 실제로 들어보고 조정한다.

### D7. text_hash 기반 증분 재생성

`text_hash = SHA256(치환 후 텍스트 + voice + speed)`

이 설계 하나로 여러 기능이 파생된다:

- 사전을 고치면 영향받는 청크만 해시가 바뀌어 재합성된다
- 캐스팅을 고치면 보이스가 바뀐 세그먼트만 재합성된다
- `synth`를 반복 실행해도 두 번째부터는 no-op
- 실패 후 재실행 시 성공분은 건너뛴다

해시에 `voice`와 `speed`를 포함하는 게 핵심이다. 텍스트만 해싱하면 캐스팅 변경이
반영되지 않는다.

### D8. LLM은 매핑만 반환한다

LLM에 본문을 재생성시키면 원문이 조용히 변형된다. 출력은 항상 구조화된 매핑이다:

- 치환 사전 후보: `{"토큰": "읽는 법"}`
- 화자 판별: `{"세그먼트 id": "화자명"}`

화자명은 규칙 단계에서 수집한 등장인물 후보 + `narrator` + `unknown`으로 제한하고,
목록 밖의 값이 오면 `unknown`으로 강등한다.

`unknown`을 명시적으로 허용하는 것이 중요하다. 억지로 찍은 오답이 "모르겠다"보다
나쁘다 — `unknown`은 내레이터 보이스로 폴백되어 티가 안 나지만, 오답은 남자가
여자 목소리로 말하는 형태로 드러난다.

### D9. 한국어 문장 분할은 라이브러리를 먼저 검토한다 (미확정)

R3.2(따옴표 내부 마침표 제외)와 R3.3(줄임표 제외)은 손으로 짜면 상태 기계가 되고,
한국어 문장부호 조합마다 예외가 붙는다. `kss`(현행 6.0.6)가 정확히 이 문제를 푸는
라이브러리다.

**아직 채택하지 않았다.** kss가 R3.2·R3.3을 우리 기대대로 처리하는지 실측하지
않았고 의존성 무게도 확인하지 않았다. T4에서 다음 순서로 결정한다:

1. R3.2~3.6을 그대로 옮긴 테스트를 먼저 쓴다
2. kss를 붙여 통과 여부를 본다
3. 통과하면 채택, 아니면 직접 구현하고 kss는 참고로만 둔다

순서가 중요하다. 라이브러리를 먼저 고르고 테스트를 거기 맞추면 요구사항이 아니라
라이브러리를 검증하게 된다.

Phase 3의 R9.2(발화 동사와 결합된 인명 추출)는 형태소 분석 여부로 정확도가 크게
갈린다 — 한국어는 `민수가` `민수는` `민수에게`처럼 조사가 붙어서 정규식으로 벗기면
오탐이 난다. `kiwipiepy`(현행 0.23.2)의 NNP 태깅이 후보이고, Phase 3에서 같은
방식으로 판단한다.

## 화자 캐스팅 전략 (Phase 3)

**풀 캐스팅을 목표로 하지 않는다.** 화자 판별이 95% 정확해도 스무 줄에 한 번
목소리가 틀린다. 이건 "조금 아쉬운" 수준이 아니라 청취를 중단하게 만드는 오류다.

단계적으로 올린다:

1. **내레이터 1명** (Phase 1)
2. **내레이터 + 대화문 성별 2종(M/F)** — 성별 추정은 화자 특정보다 훨씬 쉽고,
   규칙 단계에서 확정된 인명만으로 대부분 풀린다. 체감 개선이 가장 큰 구간
3. **주요 인물 3~4명 승격** — 등장 빈도 상위만
4. (필요하면) 전체 캐스팅

`cast.yaml`은 사람이 편집하는 파일이다:

```yaml
cast:
  narrator: { voice: M3, speed: 0.95 }
  민수:     { voice: M1, speed: 1.00 }
  지연:     { voice: F2, speed: 1.05 }
  unknown:  { voice: M3 }

overrides:
  ch3.d17: 지연
  ch7.d42: 민수
```

`overrides`가 LLM 판정을 이긴다. 증분 재생성과 결합되면 시트를 고쳤을 때 해당
세그먼트만 다시 합성되므로, LLM 정확도가 85%여도 실용적인 도구가 된다. 이
루프가 없으면 99%여도 못 쓴다.

## 한국어 화자 판별이 어려운 이유

영어 소설은 `he said` 부착률이 높지만, 한국어는 화자 표시를 생략하고 어미와
문체로 구분하는 관습이 강하다.

```
"그래서 어떻게 됐는데?"
"몰라. 나도 그때 없었으니까."
"거짓말."
"진짜라니까."
```

2인 대화는 turn-taking 규칙으로 A-B-A-B가 풀리지만, 3인 이상이 끼면 무너진다.
LLM 프롬프트에서 활용할 단서:

- 존댓말 / 반말 (상하 관계)
- 사투리, 말버릇, 호칭
- 직전 지문의 시점 인물
- 직전 확정 화자 (연속 발화 회피)

프롬프트에는 **앞 문맥 3~5줄을 반드시 포함**한다. 대화는 앞 흐름 없이 풀 수 없다.

## 비용 감각

- **TTS**: 장편 1권(60만 자 가정) → RTF 0.03에서 20~30분
- **LLM 화자 판별**: 미확정 세그먼트는 전체 텍스트의 15% 안팎이고 출력이 짧은
  JSON. 그래도 Qwen3-35B-A3B CPU 기준 장편 1권에 수 시간 단위. 배치이므로
  야간 실행으로 충분하고, 결과는 `cast.yaml`에 남아 재실행이 없다
- **저장**: opus/AAC 48kbps mono 기준 10시간 ≈ 145MB. wav 중간 캐시는
  시간당 170MB이므로 `build` 이후 정리 옵션을 둔다

## 향후 확장 지점 (지금 구현하지 않음)

- 표현 태그(`<laugh>`, `<breath>`, `<sigh>`) 활용 — 감정 판별 필요
- PostgreSQL 메타 + 잡 큐 — 여러 권 동시 처리 시
- epub 입력 — 챕터 구조가 이미 있으므로 오히려 쉽다
- 라이브러리 웹 UI (Blazor)
